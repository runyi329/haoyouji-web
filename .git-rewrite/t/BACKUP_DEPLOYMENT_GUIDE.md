# 好友记数据库自动备份部署方案

本文档为「好友记」项目提供了一套完整的数据库自动备份解决方案。该方案基于项目自带的备份脚本实现,支持将 TiDB Cloud 数据库完整导出并上传至 AWS S3 云存储,实现异地容灾和数据安全保障。

---

## 方案概述

备份方案的核心流程包含四个关键步骤,确保数据的完整性和可靠性。首先,系统使用 `mysqldump` 工具将 TiDB/MySQL 数据库完整导出为 SQL 文件。随后,生成的备份文件会被自动上传到指定的 AWS S3 存储桶中,实现异地存储和容灾保护。在备份成功上传后,系统会自动清理本地的临时文件以节省服务器磁盘空间。最后,备份脚本会在控制台输出详细的执行结果,包括文件名、大小、S3 路径以及数据库统计信息,便于后续的监控和审计。

整个备份流程已经过充分测试和优化,能够在生产环境中稳定运行。脚本支持 TiDB Cloud 的特殊配置要求,包括 `--skip-lock-tables` 和 `--no-tablespaces` 参数,确保与分布式数据库的兼容性。

## 环境要求

在生产服务器上部署备份方案之前,需要确保以下软件和工具已正确安装。Node.js 是运行备份脚本的基础环境,建议使用 v18.0 或更高版本,推荐通过 nvm (Node Version Manager) 进行安装和版本管理。包管理器 pnpm 用于安装项目依赖,需要 v9.0 或更高版本,可通过 `npm install -g pnpm` 命令全局安装。此外,系统还需要安装与数据库版本兼容的 mysql-client 工具包,以提供 `mysqldump` 命令。在 Ubuntu/Debian 系统上,可通过 `sudo apt-get install mysql-client` 命令安装。

| 软件/工具      | 版本要求        | 安装方式                                                                 |
| :------------- | :-------------- | :----------------------------------------------------------------------- |
| **Node.js**    | v18.0 或更高  | 推荐使用 nvm 进行安装和管理                   |
| **pnpm**       | v9.0 或更高   | `npm install -g pnpm`              |
| **mysql-client** | 与数据库版本兼容 | `sudo apt-get install mysql-client` |

## 配置步骤

### 环境变量配置

所有敏感配置信息都通过项目根目录下的 `.env` 文件进行管理。该文件不应提交到版本控制系统,需要在生产服务器上手动创建。配置文件包含数据库连接字符串、AWS S3 存储信息以及访问凭证。

在项目根目录创建 `.env` 文件,并填入以下配置内容:

```env
# 数据库连接字符串
# 格式: mysql://<user>:<password>@<host>:<port>/<database>
DATABASE_URL="mysql://3jHXwmWxRYXNdwU.root:YOUR_DATABASE_PASSWORD@gateway03.us-east-1.prod.aws.tidbcloud.com:4000/dWfvfUieyVkmVGc44bjad7"

# AWS S3 存储配置
S3_BUCKET="haoyouji-backups"
S3_REGION="us-east-1"

# AWS IAM 用户凭证
# 推荐创建专用IAM用户,仅授予S3存储桶的PutObject权限
AWS_ACCESS_KEY_ID="YOUR_AWS_ACCESS_KEY_ID"
AWS_SECRET_ACCESS_KEY="YOUR_AWS_SECRET_ACCESS_KEY"

# Node.js 环境
NODE_ENV="production"
```

配置时需要特别注意以下几点。`DATABASE_URL` 中的密码部分必须替换为真实的数据库密码,确保数据库用户具有足够的导出权限。AWS 凭证应使用专门为备份任务创建的 IAM 用户,遵循最小权限原则,仅授予对指定 S3 存储桶的 `PutObject` 权限。`.env` 文件包含高度敏感信息,必须设置适当的文件权限 (建议 `chmod 600 .env`),并确保已将其添加到 `.gitignore` 文件中。

### 安装项目依赖

在项目根目录执行以下命令,安装备份脚本所需的生产依赖包:

```bash
cd /path/to/haoyouji-122-new
pnpm install --prod
```

该命令会安装 AWS SDK for JavaScript v3 等必要的依赖包,整个安装过程通常在 1-2 分钟内完成。

## 自动化备份配置

为了实现真正的自动化,项目提供了一个交互式配置脚本 `setup-backup-cron.sh`,可以快速配置 Linux 系统的 cron 定时任务。

### 使用自动化配置脚本

在项目根目录执行以下命令:

```bash
chmod +x setup-backup-cron.sh
./setup-backup-cron.sh
```

脚本会引导您完成以下配置步骤:

1.  **环境检查**: 自动检测 Node.js 路径、备份脚本位置和 `.env` 文件是否存在
2.  **选择备份时间**: 提供多个预设选项或自定义 cron 表达式
3.  **创建日志目录**: 自动创建 `logs` 目录用于存储备份日志
4.  **添加定时任务**: 自动将备份任务添加到系统 crontab 中
5.  **冲突检测**: 如果检测到已存在的备份任务,会提示是否替换

配置完成后,脚本会显示详细的任务信息和常用管理命令。

### 手动配置 Cron 任务

如果您希望手动配置定时任务,可以按照以下步骤操作。首先,运行 `crontab -e` 命令打开 cron 任务编辑器。然后,在文件末尾添加以下内容:

```crontab
# 好友记数据库自动备份
0 3 * * * cd /path/to/haoyouji-122-new && /usr/bin/node scripts/backup-database.mjs >> logs/backup.log 2>&1
```

这个配置表示每天凌晨 3 点执行备份任务,并将所有输出追加到 `logs/backup.log` 文件中。您需要将 `/path/to/haoyouji-122-new` 替换为实际的项目路径,并确认 Node.js 的可执行文件路径 (可通过 `which node` 命令获取)。

保存并关闭编辑器后,cron 服务会自动加载新的定时任务。您可以通过 `crontab -l` 命令查看当前用户的所有定时任务,确认配置已生效。

### 常用 Cron 表达式

以下是一些常用的备份时间配置示例:

| 执行频率 | Cron 表达式 | 说明 |
| :------- | :---------- | :--- |
| 每天凌晨 2 点 | `0 2 * * *` | 推荐用于日常备份 |
| 每天凌晨 3 点 | `0 3 * * *` | 避开业务高峰期 |
| 每 6 小时 | `0 */6 * * *` | 适合高频备份需求 |
| 每 12 小时 | `0 */12 * * *` | 平衡频率和存储成本 |
| 每周日凌晨 2 点 | `0 2 * * 0` | 适合周度备份 |

## 监控和维护

### 查看备份日志

定时任务的执行日志会自动记录到 `logs/backup.log` 文件中。您可以使用以下命令查看最新的备份日志:

```bash
# 查看最后 50 行日志
tail -n 50 logs/backup.log

# 实时监控日志输出
tail -f logs/backup.log
```

日志文件包含了每次备份的详细信息,包括开始时间、数据库连接信息、备份文件大小、S3 上传结果以及任何错误信息。定期检查日志可以及时发现潜在问题。

### 验证 Cron 任务状态

您可以使用以下命令管理和监控 cron 定时任务:

```bash
# 查看当前用户的所有定时任务
crontab -l

# 检查 cron 服务状态
sudo systemctl status cron

# 查看 cron 系统日志
sudo grep CRON /var/log/syslog | tail -n 20
```

如果备份任务没有按预期执行,首先检查 cron 服务是否正常运行,然后查看系统日志中是否有相关错误信息。

### S3 存储管理

备份文件会持续累积在 S3 存储桶中,建议配置 S3 生命周期策略来自动管理旧备份文件。例如,可以设置以下策略:

*   保留最近 30 天的所有备份文件
*   将 30-90 天的备份文件转移到 S3 Glacier (低成本归档存储)
*   自动删除 90 天以上的备份文件

这样可以在保证数据安全的同时,有效控制存储成本。

## 故障排查

### 常见问题及解决方案

**问题 1: 数据库连接失败**

如果备份脚本报告数据库连接错误,请检查以下几点:

*   确认 `.env` 文件中的 `DATABASE_URL` 配置正确,特别是密码部分没有特殊字符转义问题
*   验证数据库服务器的网络可达性,可以使用 `telnet` 或 `nc` 命令测试端口连通性
*   确认数据库用户具有足够的权限执行 `mysqldump` 操作

**问题 2: S3 上传失败**

S3 上传失败通常是由于凭证配置错误或网络问题导致。请检查:

*   AWS 访问密钥和秘密密钥是否正确配置在 `.env` 文件中
*   IAM 用户是否具有对指定 S3 存储桶的 `s3:PutObject` 权限
*   服务器是否能够访问 AWS S3 服务 (可以尝试使用 AWS CLI 测试)

如果 S3 上传失败,备份脚本会保留本地的备份文件,不会自动删除。您可以在 `backups` 目录中找到这些文件,并手动上传或排查问题后重新运行脚本。

**问题 3: 磁盘空间不足**

如果服务器磁盘空间不足,备份任务可能会失败。建议:

*   定期检查服务器磁盘使用情况: `df -h`
*   确保 `backups` 目录有足够的空间存储临时备份文件
*   如果 S3 上传成功,本地文件会被自动清理,不会长期占用空间

**问题 4: Cron 任务未执行**

如果定时任务没有按预期执行,可能的原因包括:

*   Cron 表达式配置错误,可以使用在线工具验证表达式的正确性
*   Cron 服务未运行,使用 `sudo systemctl status cron` 检查服务状态
*   脚本路径或 Node.js 路径配置错误,确保使用绝对路径
*   环境变量未正确加载,cron 任务的环境与交互式 shell 不同,可能需要在脚本中显式设置环境变量

## 数据恢复

虽然本方案主要关注备份,但了解如何恢复数据同样重要。以下是基本的恢复步骤:

### 从 S3 下载备份文件

首先,使用 AWS CLI 或控制台从 S3 下载需要恢复的备份文件:

```bash
aws s3 cp s3://haoyouji-backups/database-backups/haoyouji_backup_2026-02-13T14-30-25.sql ./restore.sql
```

### 恢复数据库

使用 `mysql` 命令将备份文件导入数据库:

```bash
mysql -h gateway03.us-east-1.prod.aws.tidbcloud.com \
      -P 4000 \
      -u 3jHXwmWxRYXNdwU.root \
      -p \
      dWfvfUieyVkmVGc44bjad7 < restore.sql
```

执行此操作前,强烈建议先在测试环境中验证备份文件的完整性和可用性。数据恢复操作具有高风险,可能会覆盖现有数据,务必谨慎操作。

## 安全建议

为了确保备份方案的安全性,建议遵循以下最佳实践:

1.  **最小权限原则**: 为备份任务创建专用的 IAM 用户,仅授予必要的 S3 权限,避免使用根账户凭证
2.  **凭证保护**: 确保 `.env` 文件的权限设置为 `600`,只有文件所有者可以读写
3.  **定期轮换**: 定期更换 AWS 访问密钥和数据库密码,降低凭证泄露风险
4.  **加密传输**: AWS SDK 默认使用 HTTPS 加密传输,确保备份文件在传输过程中的安全性
5.  **S3 加密**: 建议在 S3 存储桶中启用服务器端加密 (SSE-S3 或 SSE-KMS),保护静态数据
6.  **访问审计**: 启用 AWS CloudTrail 记录 S3 访问日志,便于安全审计和异常检测
