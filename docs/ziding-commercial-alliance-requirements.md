# 紫鼎商业联盟商城：需求讨论稿

> **状态：首版热预览开发中；首批商品已写入项目商品库，待页面确认后统一推送上线。**
>
> 项目入口：`https://www.jiangyuchen.cn/p/proj_stn4q7`
>
> 本文用于逐项记录已确认规则、可复用能力与待确认项；后续实施以本文和用户的最新指示为准。

## 1. 已确认的项目定位

- 项目名称：**紫鼎商业联盟**。
- 形态：移动端优先的独立商城前台与项目专属后台。
- 用户与管理员使用**同一套前台首页和商品页面**；仅项目管理员在首页右上角额外看到“后台管理”入口。
- 不使用在线支付、钱包扣款或支付网关。
- 用户下单后上传**付款凭证截图**；紫鼎项目管理员人工核对并确认收款。
- 项目用户分为两个等级：**初级用户**与**高级用户**。商品、套餐、进货价和可见权益后续按等级配置。
- “盈盈”后续应成为**紫鼎商业联盟项目管理员**，不改变其全网站权限，也不授予全局管理员身份。

## 2. 视觉与交互基调

参考用户提供的“初级代理 / 高级代理”物料：

- 主色：深紫、紫罗兰；辅助色：米白、香槟金。
- 质感：丝绸流光背景、细金线、圆角米白信息卡；避免通用蓝白商城风格。
- 字体与信息层次：大标题和价格有明确层级；移动端保持留白、可读性和紧凑度。
- 所有页面在手机宽度优先设计；后台同样保持与前台一致的紫金视觉体系。
- 后续产品图片、Logo、Banner 与按钮素材均使用正式 COS 地址，不把临时本地图片作为生产资源。
- **已确认执行规则：** 紫鼎项目的商品图、Logo、Banner、页面配图与按钮图片，均须经服务端上传至腾讯云 COS；商品图统一写入 `assets/ziding-commercial-alliance/products/`，服务端自动压缩为 WebP 后回写 COS 公网地址。付款凭证仍使用私有 COS 对象与短时授权链接，不能复用公开图片逻辑。

## 3. 角色与权限

| 角色 | 可见内容 | 主要能力 |
|---|---|---|
| 初级用户 | 前台、商品、购物车、订单、地址簿、付款凭证上传 | 按初级身份的可购商品/套餐与价格下单；查看和管理自己的订单 |
| 高级用户 | 与初级用户相同的前台框架 | 按高级身份的可购商品/套餐与价格下单；查看和管理自己的订单 |
| 紫鼎项目管理员 | 与用户相同的前台，右上角多“后台管理”入口 | 管理商品、分类、用户等级、订单、付款凭证核验、发货、物流与项目设置 |

### 权限原则

1. 管理员权限必须**绑定 `proj_stn4q7` 项目范围**，不能复用或提升为全站管理员。
2. 订单、地址、付款凭证、商品和后台数据都必须按项目隔离；不能与米伴、牙伴或其他项目互相读取。
3. 用户只能看自己的地址、订单和付款凭证；项目管理员只能看紫鼎项目范围内的订单及其凭证。

## 4. 商品、购物车与地址流程

### 4.1 下单基本流程

1. 用户浏览商品、查看详情、选择规格/数量后加入购物车或直接拍下。
2. 结算页必须填写或选择收货地址、确认商品与总金额；用户可填写订单备注。
3. 提交后生成订单，但**不发生任何在线支付或账户扣款**。
4. 系统引导用户上传付款凭证；凭证上传后由后台人工核验。

### 4.2 常用地址

复用米伴已验证的交互模式，但数据库与 API 必须为紫鼎项目单独隔离：

- 地址簿支持新增、编辑、删除、设为默认地址、下单时选择已有地址。
- 每个地址包含：标签（家/公司/父母家或自定义）、收货人、手机号、省/直辖市/自治区、市/地区、区/县、详细地址、是否默认。
- 使用现有完整的省—市—区县三级联动数据源：
  - 普通省份：依次选择省、城市/地区、区县。
  - 北京、天津、上海、重庆：选择直辖市后跳过重复市级，直接选择区县。
  - 最后填写街道、楼栋、门牌号等详细地址。
- 下单时默认优先带出默认地址；用户也可展开地址簿改选。
- 订单保存**地址快照**。日后用户修改地址簿，不回写或改变已创建订单的收货信息。

> 可直接借鉴的现有实现：米伴 `AddressBook.tsx`、`regionData.ts` 与地址簿的新增/编辑/默认地址交互。紫鼎不可直接使用 `miban_addresses` 表，以免跨项目泄露用户地址。

## 5. 付款凭证与订单状态机

### 5.1 用户侧可见状态

| 内部状态建议 | 用户显示 | 进入条件 | 用户下一步 |
|---|---|---|---|
| `awaiting_proof` | 已拍下 · 待上传凭证 | 用户提交订单 | 上传付款凭证，或取消订单 |
| `proof_submitted` | 待确认 | 用户已上传凭证 | 等待管理员人工核验 |
| `proof_rejected` | 凭证待补充 | 管理员驳回凭证并填写原因 | 查看原因后重新上传凭证 |
| `confirmed` | 已确认 · 等待发货 | 管理员确认收到款项 | 等待发货；查看订单与收货信息 |
| `shipped` | 已发货 | 管理员填写或确认物流信息 | 查看物流；可提前确认收货 |
| `completed` | 已完成 | 用户确认收货，或发货满设定天数后系统自动收货 | 查看历史订单 |
| `cancelled` | 已取消 | 用户在可取消阶段取消，或管理员取消 | 查看取消原因；不涉及系统自动退款 |

### 5.2 管理员操作及通知

1. 管理员在后台订单详情中查看**私有付款凭证**、付款时间、订单金额、地址和商品快照。
2. 管理员可：
   - **确认收款**：订单转为“已确认 · 等待发货”，立即向用户发送站内通知；
   - **驳回凭证**：必须填写原因，用户收到站内通知并可以重新上传；
   - **取消订单**：记录取消原因并通知用户；
   - **确认发货**：填写物流公司和物流单号（如暂时没有单号，也应保留管理员备注和后续补录能力）。
3. 用户端“我的订单”展示状态时间线、管理员通知、物流信息及付款凭证上传入口。
4. 第一阶段通知采用**站内通知 + 订单状态更新**；短信、微信模板消息等外部推送如需要，后续单独接入和确认。

### 5.3 自动收货

- 用户在发货后可主动点击“确认收货”。
- 系统应提供项目级设置：`发货后 N 天自动确认收货`。
- **待确认参数：N 的默认值。** 建议默认 7 天，管理员可在紫鼎后台设置；在用户确定前不硬编码为固定天数。
- 自动收货必须在服务器端定时任务执行，不能依赖用户打开页面。

### 5.4 金额与审计原则

- 订单金额、商品价格、商品名称、规格和收货地址均在下单时保存快照；后续改价、改商品、改地址不影响历史订单。
- 不接入线上付款，因此取消订单只改变订单状态，不触发系统退款。
- 付款凭证的上传、替换、查看、确认、驳回、取消、发货及自动收货均需要写入订单操作日志，含操作者、时间、动作、备注和状态变化。

- 牙伴现有商城以微信/支付宝支付状态为主，不能作为紫鼎的支付链路；紫鼎必须改为“订单创建 → 上传凭证 → 人工确认”。

### 付款凭证安全规则

付款凭证不能沿用当前公开图片的直接 URL 方式。开发时必须：

1. 上传至专门的 `ziding-commercial-alliance/payment-proofs/` 前缀；
2. 使用私有对象权限；如现有公共桶策略不能保证对象私有，则改用单独的私有 COS 桶；
3. 不在前端或数据库中暴露永久公开 URL；
4. 只由后端按订单归属和项目管理员权限生成短时效预览链接；
5. 管理员查看凭证的操作记录需可追溯。

> 对象前缀只用于分类，不构成访问控制；付款凭证的私有权限必须由 COS 对象 ACL、桶策略或独立私有桶落实。

## 9. 架构与商业运营建议

### 9.1 上线前必须确定的规则

| 优先级 | 建议 | 原因与推荐做法 |
|---|---|---|
| P0 | **用户等级由谁授予** | 初级/高级不能由用户自行选择。建议仅由紫鼎项目管理员在后台授予、调整或停用；每一次调整留下原因和时间。等级改变只影响未来新订单，历史订单价格快照不回写。 |
| P0 | **代理套餐是固定包还是任选包** | 参考物料中的“任选一组”，应尽早确定为：固定组合、在指定商品中任选 N 件，或主套餐加可选加购。后两种需要专门的套餐规则和库存校验，不能只用普通单 SKU 商品代替。 |
| P0 | **线下收款指引如何配置** | 因没有在线支付，应在后台配置“收款说明”：收款人、开户行/账号或收款二维码、付款备注格式、客服联系方式。必须可随时替换，不应硬编码在页面中。 |
| P0 | **付款凭证核验标准** | 建议支持 1–3 张图片，并让用户填写付款人姓名与转账尾号/备注；管理员确认或驳回时必须留下审核意见。这样能显著降低同金额订单、截图不清或错传凭证的人工核对成本。 |
| P0 | **待上传凭证订单的库存占用时长** | 推荐“创建订单后先占用库存 24 小时；到期未上传凭证自动取消并释放库存”。上传凭证后继续占用，直到管理员确认、驳回或取消。时长应在项目设置中可配置。 |
| P0 | **发货与售后范围** | 明确是否所有商品都必须填物流单号；是否有自提/无需物流商品；支付后但发货前、已发货后分别如何取消或售后。线下退款可在系统中记录“已人工退款”，但系统不主动发起资金退款。 |
| P0 | **自动收货天数** | 建议后台可设置，默认 7 天；用户可提前确认收货，管理员可以对个别订单延期。自动完成必须由服务端任务执行并写入日志。 |

### 9.2 最应优先建设的运营能力

1. **首页立即识别等级与权益**：用户进入后直接看到“当前身份：初级/高级代理”、相应价格与套餐权益；不应让用户猜自己可以购买什么。
2. **项目专属管理员权限**：建议至少分为“项目负责人”“订单管理员”“内容/商品管理员”三档。第一阶段也可以先只启用前两档，但数据表和鉴权应预留扩展。
3. **后台待办工作台**：顶部优先显示“待上传凭证、待确认、待发货、即将自动收货、库存不足”五个数字；管理员不需要逐页翻找订单。
4. **订单时间线与站内通知**：每个订单显示已拍下、已上传、已确认、已发货、已完成的时间；管理员确认、驳回、发货都自动产生站内通知。
5. **商品信息标准化**：每个商品至少有主图、规格、零售价/对应等级价、库存、发货说明、售后说明、成分或产品参数。涉及营养、健康、护肤等品类时，避免使用未经证实的医疗或治疗承诺。
6. **按订单快照结算**：商品名称、图、价格、等级价、规格、地址和收款核验结果均在下单时固化，杜绝“后来改价导致历史订单金额变化”。
7. **合规和隐私底线**：地址、电话、付款凭证均为敏感业务数据；后台列表默认掩码，查看明文、导出、下载凭证都写审计记录。付款凭证必须存私有 COS，不能使用公开图片链接。

### 9.3 推荐的分阶段建设顺序

| 阶段 | 范围 | 目标 |
|---|---|---|
| 第一阶段：可开单 | 项目专属角色、用户等级、商品/套餐、购物车、独立地址簿、下单、私有凭证上传、后台人工确认 | 让用户能安全地下单并由管理员完成收款确认 |
| 第二阶段：可履约 | 发货、物流单号、订单时间线、站内通知、自动收货、后台待办、库存预占与释放 | 减少管理员手工追单和用户询问 |
| 第三阶段：可运营 | Banner/活动配置、数据看板、商品销量与待办统计、客户筛选、订单导出、售后登记 | 让管理员持续运营而非依赖开发人员改页面 |
| 第四阶段：视业务决定 | 邀请关系、团队、佣金、分销、会员升级自动化、外部消息通知 | 仅在基础交易闭环稳定后再做，避免一开始把交易和分佣规则耦合得过深 |

### 9.4 当前项目管理员能力的核验结论

- 已核验：盈盈账号当前已绑定紫鼎项目版本 `proj_stn4q7`，可进入该项目版本。
- 当前平台数据结构尚没有通用的“项目管理员成员表”；用户全局 `role` 只有全站角色，不能直接用于紫鼎管理员授权。
- 因此实施时应新增**项目范围角色映射**（例如项目、用户、角色、启用状态、授权人、授权时间），以保证“盈盈是紫鼎管理员”不会影响任何其他项目和全网站权限。

## 10. 建议由项目负责人逐项拍板的清单

1. 初级与高级用户是管理员手动授予，还是购买某代理套餐后自动升级？
2. 高级代理 210 元、初级代理 280 元是整套固定价，还是可以任选商品形成套餐？
3. 普通零售商品是否也向两种用户开放，是否显示不同价格？
4. 一笔订单最多上传几张凭证：建议 3 张；是否需要填写付款人姓名及转账尾号？
5. 未上传凭证多久自动取消并释放库存：建议 24 小时。
6. 发货后多久自动确认收货：建议默认 7 天，后台可调。
7. 订单通知只做站内通知，还是还要接入微信/短信？第一阶段推荐站内通知。
8. 客服入口使用什么形式：客服微信、电话号码、在线留言，或三者都要？
9. 是否第一阶段就需要邀请、团队或佣金？建议先不做，先验证商品—付款凭证—发货的闭环。

## 11. 月度阶梯加权积分（已确认纳入）

### 11.1 业务目标

- 用户每月的有效订购额达到不同阶梯后，按对应**加权系数**获得积分。
- 规则由紫鼎项目管理员在后台编辑、启用、排序；不能把阶梯或倍率写死在前端。
- 用户端需要在“我的”或订单区域清楚显示：**本月有效订购额、当前加权系数、本月已获积分、距下一档还差多少**。

### 11.2 推荐且符合示例的计算口径

以用户给出的示例为准，采用“**当月累计总额，按当前最高档统一重算**”的方式：

| 已确认收款的当月累计金额 | 当前倍率 | 当月目标积分 |
|---:|---:|---:|
| 1,000 | 1.0 | 1,000 分 |
| 2,000 | 1.2 | 2,400 分 |

因此，用户先完成一笔 1,000 元订单获得 1,000 分；同月第二笔完成后累计达到 2,000 元，系统不只是再给 1,200 分，而是将当月目标积分重算为 2,400 分，**补发差额 1,400 分**。这才与“买了 2,000，送 2,400 分”一致。

### 11.3 记分时点与异常处理

1. 只在管理员**确认收款**后计入“当月有效订购额”；创建订单、待上传凭证、待确认凭证阶段均不预发积分。
2. 每次确认一笔订单后，系统重算该用户当月累计有效金额、命中的最高阶梯与目标积分，并写入“本次新增/补发积分”流水。
3. 订单被取消或登记人工退款时，系统重算该月金额并生成冲减流水，避免确认后取消订单仍保留积分。
4. 订单金额、命中倍率、目标积分和本次积分调整均写入审计日志，保证管理员可追溯。
5. 初期只显示和累计积分，不提前做积分兑换、过期或抵扣规则；兑换规则等业务明确后另行接入。

### 11.4 管理后台设置

- 管理员可添加、编辑、停用、排序阶梯：`当月有效金额门槛`、`加权系数`、`规则说明`、`生效起始月份`。
- 阶梯从低到高展示，默认包含 `0 → 1.0`；系统校验门槛不得重复、倍率不得小于 0。
- 已发生月份的规则保留版本快照。管理员修改规则默认只影响后续确认订单或指定未来月份，不能静默改写已发积分。

### 11.5 待项目负责人明确的细节

1. 示例中“买 1,000 点 / 2,000 点”是否以**人民币实付订单金额**为计算基数；当前方案暂按人民币订单金额设计。
2. 积分是否永久有效，还是按自然年或会员周期清零；第一阶段建议先不设失效。
3. 是否所有商品都计积分，或仅代理/指定商品计积分；第一阶段可通过商品的“参与积分”开关控制。

## 12. 前台与后台视觉方向（已确认）

### 12.1 总原则

- 仅借用现有物料的**紫金色彩关系**，不复刻其海报化、促销化的视觉语言。
- 前台定位为“高端护肤 / 健康管理品牌”的移动端商城：安静、有留白、可信赖、以商品和服务信息为主。
- 不使用大面积紫色丝绸背景、粗重金色描边、立体金框、超大促销数字、排名圆牌、密集渐变或海报式堆叠文字。
- 先为 390–430px 手机宽度设计；桌面端仅在此基础上自然放宽，不能反向压缩桌面布局。

### 12.2 建议的视觉令牌

| 用途 | 建议色彩 | 使用原则 |
|---|---|---|
| 主背景 | 暖象牙白 `#F8F5F1` | 大面积留白，保持清洁与轻盈 |
| 主文字 / 深色区 | 深茄紫 `#28152F` | 品牌名称、主按钮、重要标题 |
| 辅助紫 | 灰紫 `#765777` | 标签、次级强调、状态点缀 |
| 点缀金 | 哑光香槟金 `#B89A68` | 只用于细线、会员等级、关键小图标，不大面积填充 |
| 边界 / 卡片底色 | 米灰 `#E9E1D8` / 纯白 | 极细边界与柔和层级，不做厚重描边 |

### 12.3 前台页面规则

1. 首页采用简洁头部、会员身份/本月积分摘要、编辑式商品陈列和清晰底部导航；第一屏不做传统“代理价海报”。
2. 商品卡以真实商品图、名称、规格、价格和库存/权益为核心；价格不做夸张字号，不以“金框 + 巨型数字”制造促销感。
3. 会员身份和积分使用低饱和小标签、细线和清楚文案表达，不能做成奖牌、皇冠或高饱和渐变。
4. 下单、上传付款凭证、订单时间线采用分步但不啰嗦的流程设计；每一步说明下一步需要什么，避免让用户猜测。
5. 字体以系统中文无衬线字体为正文；仅可在品牌/故事标题的少量位置使用克制的衬线感，不使用夸张书法字或变形艺术字。

### 12.4 项目后台规则

- 管理员仍然进入同一前台，右上角出现“后台管理”入口；进入后切换为清晰的轻量运营工作台。
- 后台优先展示待确认凭证、待发货、即将自动收货、库存不足和本月积分发放等待办；使用状态颜色和数字层级，不使用海报装饰。
- 表格在手机上转为信息卡列表，关键操作固定在易触达区域，付款凭证预览和下载保持一键完成。
